# План доработки текста ВКР

## Цель доработки

Привести пояснительную записку к состоянию, в котором она честно и доказательно
отражает фактическое состояние проекта: реализованные функции, частично
подтвержденные требования, ограничения MVP и направления дальнейшей работы.

## Этап 1. Согласовать ВКР с ТЗ и приемкой

1. Добавить в раздел 2 или 4 матрицу соответствия требованиям:
   - номер или краткое название требования;
   - источник требования: ТЗ, архитектурное ограничение, критерий приемки;
   - модуль реализации;
   - проверяющий артефакт: тест, документ, конфиг, endpoint;
   - статус: выполнено, частично выполнено, не подтверждено.
2. Отдельно отметить требования, которые сейчас нельзя считать полностью
   закрытыми:
   - HTTPS backend API;
   - полноценный защищенный контур RPC через nginx + mTLS;
   - end-to-end проверка с реальным Bitcoin Core/regtest;
   - фактическое покрытие backend >= 80%;
   - производительные испытания.
3. Переписать слишком сильные формулировки в реферате, разделе 4 и заключении:
   вместо абсолютного "подтверждено" использовать формулировки с указанием
   уровня проверки.

## Этап 2. Усилить теоретическую часть

1. Расширить анализ существующих решений:
   - Bitcoin Core RPC/indexes;
   - Electrs/Esplora;
   - BlockSci;
   - Bitcoin ETL;
   - публичные explorer API.
2. Добавить таблицу сравнения по критериям:
   - контроль над источником данных;
   - поддержка адресных индексов;
   - работа с reorg;
   - доступность mempool-данных;
   - возможность локального развертывания;
   - пригодность для требований ВКР.
3. Сделать вывод, почему для проекта выбран собственный индексатор в формате
   модульного stateless-монолита.

## Этап 3. Детализировать проектирование

1. В разделе модели данных добавить таблицу с ключевыми полями:
   - таблица;
   - основные поля;
   - первичный ключ;
   - уникальные ограничения;
   - индексы;
   - назначение в процессе индексации.
2. Добавить или обновить ER/DFD/C4-диаграммы так, чтобы они были связаны с
   текстом, а не выглядели отдельными иллюстрациями.
3. В разделе интерфейсов привести основные группы endpoint'ов и короткие
   примеры ответов для jobs, nodes и data API.
4. Явно описать жизненный цикл job и допустимые переходы статусов.

## Этап 4. Усилить раздел реализации

1. Заменить слабые листинги на фрагменты, которые показывают инженерную
   сложность:
   - транзакционная запись блока;
   - идемпотентная запись и upsert;
   - обработка reorg;
   - синхронизация mempool;
   - маршрутизация API и формат ошибок;
   - миграции PostgreSQL.
2. Для каждого листинга добавить пояснение:
   - какую проблему решает фрагмент;
   - какое требование ТЗ он закрывает;
   - как он проверяется тестами.
3. Описать важные решения из кода:
   - advisory lock на высоту блока;
   - разделение confirmed/mempool/dropped/orphaned;
   - пересборка агрегатов после reorg;
   - хранение прогресса jobs в БД;
   - экспорт Prometheus-метрик.

## Этап 5. Переписать раздел испытаний

1. Оформить раздел 4 как протокол испытаний:
   - окружение;
   - команды запуска;
   - используемые тестовые данные;
   - число тестов;
   - результат выполнения;
   - ограничения проверки.
2. Добавить таблицу проверок:
   - jobs lifecycle;
   - data API;
   - storage pipeline;
   - idempotency;
   - mempool;
   - reorg;
   - metrics;
   - admin panel;
   - CLI.
3. Честно указать, что текущие интеграционные тесты используют PostgreSQL +
   mock RPC, а не реальный Bitcoin Core/regtest.
4. Если получится, добавить результаты:
   - `cargo check`;
   - `cargo test -- --ignored`;
   - `cargo llvm-cov`;
   - Docker Compose smoke test.
5. Если результаты не получены, описать это как ограничение текущей проверки,
   а не как выполненное требование.

## Этап 6. Усилить практическую значимость

1. Добавить 2-3 конкретных сценария применения:
   - получение текущего баланса адреса;
   - поиск транзакций по адресу;
   - мониторинг прогресса full-sync;
   - просмотр mempool-транзакций по адресу.
2. Для каждого сценария показать:
   - используемые endpoint'ы;
   - таблицы БД;
   - ожидаемый результат;
   - отличие от прямой работы с Bitcoin Core RPC.
3. Если есть возможность, добавить минимальные измерения времени ответа или
   объема обработанных данных.

## Этап 7. Привести оформление к финальному виду

1. Исправить тему на титульном листе:
   `Система индексации блокчейн данных`.
2. Разнести файлы по смыслу:
   - теоретическая часть;
   - проектирование;
   - реализация;
   - оценка качества;
   - практическая значимость;
   - заключение.
3. Переименовать приложения:
   - диаграмма контейнерного развертывания;
   - структура репозитория;
   - критерии приемки;
   - фрагмент конфигурации.
4. Убрать дублирующее приложение со списком источников или заменить его на
   полезный технический артефакт.
5. Проверить LaTeX-лог и исправить `Overfull`-предупреждения.
6. Убедиться, что задание на ВКР, рецензент и консультанты заполнены по
   требованиям кафедры.

## Приоритет выполнения

1. Сначала закрыть расхождение между ВКР, ТЗ и `doc/acceptance`.
2. Затем переписать раздел испытаний и добавить доказательные таблицы.
3. После этого усилить реализацию и модель данных.
4. В последнюю очередь полировать приложения, названия файлов и верстку.
